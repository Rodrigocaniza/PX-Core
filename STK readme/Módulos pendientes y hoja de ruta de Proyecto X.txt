# 27. Módulos pendientes y hoja de ruta de Proyecto X

Esta sección reúne las funciones, módulos y mejoras que fueron planteadas durante el desarrollo, pero que todavía no están completamente implementadas.

No todos los puntos tienen la misma prioridad. Algunos forman parte del núcleo inmediato de BC Gestión y otros corresponden a una ampliación futura de Proyecto X.

---

## 27.1. Estado general del desarrollo

Proyecto X ya cuenta con una base funcional que permite avanzar sobre la gestión financiera y administrativa.

Entre las funciones que ya fueron desarrolladas o probadas se encuentran:

* Menú principal modular.
* Registro de ideas.
* Registro y administración de proyectos.
* Registro básico de horas.
* Registro de movimientos.
* Visualización de movimientos.
* Modificación de movimientos.
* Eliminación de movimientos.
* Importación de movimientos desde Excel.
* Filtrado por período.
* Eliminación completa de períodos importados incorrectamente.
* Sincronización del proyecto mediante GitHub.
* Uso del sistema desde diferentes computadoras mediante `git pull` y `git push`.

La función de eliminación de períodos ya fue probada y funciona correctamente.

A partir de esta base, el desarrollo debe continuar por módulos, evitando intentar construir todo el sistema simultáneamente.

# 28. Pendientes inmediatos del núcleo financiero

## 28.1. Consolidar la carga diaria

La carga de movimientos debe organizarse principalmente por fecha.

El flujo esperado es:

1. Seleccionar la fecha.
2. Registrar todo lo ocurrido ese día.
3. Ingresar ingresos.
4. Ingresar egresos.
5. Registrar transferencias internas.
6. Registrar depósitos.
7. Revisar el resumen diario.
8. Confirmar la carga.

Esto reemplazaría la necesidad de ingresar repetidamente la fecha en cada operación.

También permitiría verificar fácilmente si un día quedó completamente cargado.

---

## 28.2. Unificar la gestión de movimientos

Las opciones relacionadas con movimientos deben estar agrupadas dentro de un único menú.

El módulo debería contener:

1. Registrar movimientos del día.
2. Ver movimientos.
3. Modificar movimientos.
4. Eliminar movimientos.
5. Buscar o filtrar movimientos.
6. Importar movimientos.
7. Administrar períodos.
8. Volver.

La opción **Volver** debe mantenerse siempre como número **0** en todos los menús del sistema.

---

## 28.3. Filtros generales por mes y año

Todo listado que pueda crecer debe solicitar primero el período que se desea consultar.

Ejemplo:

**07-2026**

Este criterio debe aplicarse a:

* Movimientos.
* Préstamos.
* Cuotas.
* Retiros de socios.
* Gastos fijos.
* Informes.
* Cierres.
* Depósitos.
* Tarjetas de crédito.
* Mantenimientos realizados.
* Planillas de asociaciones.

El objetivo es evitar listas excesivamente largas y facilitar la revisión mensual.

---

## 28.4. Validación de movimientos duplicados

El sistema debe identificar posibles duplicaciones, especialmente después de una importación.

Podría comparar:

* Fecha.
* Monto.
* Tipo.
* Descripción.
* Cuenta.
* Unidad de negocio.
* Número de comprobante.

El sistema no debería bloquear automáticamente todos los movimientos iguales, porque pueden existir operaciones legítimamente repetidas.

Debe mostrar una advertencia para que el usuario decida.

---

## 28.5. Numeración interna de movimientos

Cada movimiento debe recibir un identificador único.

Ejemplo:

**MOV-2026-000154**

Este código permitiría:

* Buscar una operación.
* Modificarla.
* Relacionarla con préstamos.
* Relacionarla con socios.
* Vincularla a documentos.
* Registrar auditorías.
* Evitar confusión entre movimientos similares.

# 46. Protocolo de trabajo entre computadoras

## Al comenzar

2. Abrir la terminal.
3. Ejecutar `git pull`.
4. Confirmar que no existan conflictos.
5. Iniciar el trabajo.

## Al terminar

1. Probar los cambios.
2. Guardar todos los archivos.
3. Ejecutar `git status`.
4. Ejecutar `git add .`.
5. Crear el commit.
6. Ejecutar `git push`.
7. Confirmar que los cambios subieron correctamente.
8. Registrar el avance y las horas.

Este protocolo evita trabajar sobre versiones antiguas y perder cambios.

# 47. Migración futura a base de datos

La versión inicial utiliza archivos simples y planillas porque permiten aprender y construir las funciones progresivamente.

Sin embargo, el sistema deberá migrar a una base de datos.

## Primera opción recomendada

**SQLite**

Ventajas:

* No requiere servidor.
* Funciona localmente.
* Se integra bien con Python.
* Permite relaciones entre módulos.
* Reduce duplicaciones.
* Facilita búsquedas.
* Permite respaldos.
* Es adecuada para una primera versión empresarial.

## Evolución posterior

Si Proyecto X se convierte en una aplicación usada simultáneamente desde varias computadoras, podría migrarse a:

* PostgreSQL.
* Una aplicación web.
* Un servidor local o en la nube.
* Gestión de usuarios y permisos.

# 51. Criterio para agregar nuevos módulos

Antes de crear un nuevo módulo debe responderse:

1. ¿Qué problema empresarial resuelve?
2. ¿Quién lo utilizará?
3. ¿Qué información necesita?
4. ¿Qué resultado debe producir?
5. ¿Se relaciona con un módulo existente?
6. ¿La información ya se carga en otro lugar?
7. ¿Es prioritario o puede esperar?
8. ¿Puede desarrollarse sin afectar el núcleo actual?
